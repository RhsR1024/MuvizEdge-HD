# 157：启动采集诊断与一次服务重建试验

日期：2026-10-05。版本：157 / 2.1.4.0-adaptive-zh15。用户授权在156基础上补充诊断并实现可对照的恢复试验。

## 已知事实与实验范围

156日志同时存在后台成功和必须进入界面才能恢复的会话。通知监听通常先于BOOT_COMPLETED建立服务，单靠这些日志不能确定厂商后台录音资格差异的根因。参见 [156启动复核](STARTUP_INVESTIGATION156.md)。157仅增加“持续失败后完整重建一次AppService”试验；不同时延迟首次服务启动，以便比较结果。

原有普通音频重试和保守/增强设置继续保留，增强模式仍默认关闭。新试验默认仅在Android 11（API30）、大屏模式、车机音频兼容开启时生效。“显示与语言 → 开机采集恢复（试验）”可关闭。Android13手机不会自动进入这项完整服务重建路径，诊断改进在手机也生效。

## 触发、退出与保护

全部满足才开始计时：已解锁、亮屏、运行时录音及悬浮授权、音乐悬浮功能开启、服务就绪、应用界面在后台稳定、确有播放且需要采集、系统有效RECORD_AUDIO AppOp为ignored、当前服务建立后发生过原生采集失败、没有近期后台FFT。

系统运行至少60秒、当前服务存在至少10秒，满足上述条件连续30秒后才请求重建。任意条件不满足会清掉连续失败计时。已在本轮收到有效后台FFT（即使数值全零），不再执行本试验，避免破坏已工作的服务。正常的Visualizer音频恢复仍可处理后续断流。

每次真正开机或确认熄屏/深睡至少60秒后的唤醒，最多消耗一次重建预算。重复亮屏、解锁、短暂熄屏不会补预算。boot_count未知时不自动试验。周期、已用预算、后台FFT健康标记使用独立SharedPreferences保存，服务或进程重建不应重获机会。预算先在工作线程commit成功，再于主线程复核播放、权限、健康与目标服务后stopSelf；复核取消也保留已用预算，宁可少试一次。对旧服务销毁和新服务就绪均有8秒超时，不会第二次stopSelf。

旧AppService.onDestroy入口先移除辅助监控、播放回调、导航观察器；原程序继续清理控制器、窗口和接收器。主线程250ms后继续建立服务，因此不会在原清理栈中重入。停止期间推迟普通启动请求，显式停止命令取消事务；原来的看门恢复继续保留。若停止后用户仅关闭本试验而未关闭应用功能，仍完成服务恢复，避免功能被留在关闭状态。

这是重新建立Android Service及其控制器，不是重建整个进程。原音频引擎ib.e.u是首页与后台共用单例，仍可能复用；不强行清空它，不承诺所有音频对象都已重新分配。日志记录引擎身份供核验。没有自动打开Activity、篡改权限或伪造节奏。

## 新增诊断证据

- STARTUP_STAGE：进程注册、开机广播、通知监听、服务建立/就绪、界面开始、AppOp回调、新唤醒周期、重建前后与1/5/30秒结果。含系统两种时钟、boot/cycle/service generation、进程重要级及原因、录音有效/原始模式、前台服务状态、锁定/亮屏/节电/后台限制和播放器状态。
- RECORD_OP_WATCH：注册自身录音AppOp变化监听；支持时包含前后台模式变化，仍保留轮询。监听只是观测，不赋予权限；回调缺失也不等于系统没有变化。
- FIRST_FFT / FIRST_NONZERO_FFT：在原始FFT回调现场记录时间。以当前Visualizer身份、服务代次和Activity状态区分background_overlay、foreground_shared_engine、preview_or_other；分来源和唤醒周期记录首帧，旧Visualizer回调不作为新服务证据。
- first_background_fft_this_cycle：当前周期首次后台FFT，用于健康保护。它证明收到后台回调，不单独证明屏幕已经显示。
- FIRST_OVERLAY_DRAW：当前悬浮View已attached/shown时的首次成功绘制、尺寸/可见矩形/alpha。接入点在surface提交前，所以明确记录compositorVisibility=unknown，不能代替实拍确认。
- STARTUP_RECREATE_STATE：等待、条件不符、已健康或已用预算。STARTUP_STAGE中的recreate_*描述停止、原清理返回、新服务结果或取消/超时原因。
- AUDIO_PLAYBACK_CALLBACK记录回调的音频usage/content类型；回调注册/注销留痕。重复同类原生异常首条保留堆栈，其后按分钟汇总次数，导出头保留本进程累计计数。

频谱首帧仍以真实回调为准；播放会话只说明播放器状态。时间间隔用e=elapsedRealtime计算，不能直接减可能受TIME_SET校时影响的墙钟。

## 日志容量与导出

总持久文件容量仍不超过2MiB：常规运行区1792KiB + 独立启动关键事件区256KiB，各自两段轮转。导出先放诊断头和启动区，再放常规区，总导出含头不超过2MiB。事件在两区可能重复；分析时用session/e/事件内容去重，不能双倍计算次数。启动区也会滚动，不能无限保存历史。升级缩小常规区时保留旧文件末尾的UTF-8内容，不直接清空。

导出沿用Download/MuvizEdge/MuvizEdge-yyyy-MM-dd-HHmmss-SSS.txt，无新增存储权限。私有日志和签名材料不入库。

## 验证与下一轮

新增50项StartupCapturePolicyTest和9项日志检查；总计749项JVM检查，另有8项API解析检查。实际构建结果见verification/release157.json。逻辑/静态/签名校验无法证明厂商ROM会在服务重建后赋予录音资格，157尚待车机与手机实测。

覆盖安装后先打开一次核对功能开关，再真正重启或长休眠。重启后不要先进入Muviz，直接播放约90秒，观察有无律动及出现延迟，然后进入Muviz导出日志。即使没有律动也导出；导出前打开界面改变的状态已与此前后台时间线分开记录。至少比较数次重启与长短休眠，必要时关闭试验同机对照，保守/增强模式尽量保持相同。

重点核查：是否满足30秒条件、是否仅出现一次recreate_stop_requested、旧generation确实结束且新generation就绪、AppOp何时变化、首次background_overlay非零FFT是否早于ACTIVITY_START、既有正常播放是否完全未触发试验。复测暂停继续、导航栏显隐、权限撤销、关闭功能、手机后台播放；不得把收到服务命令或服务就绪当作成功。
