## 工程来源和目标

从用户提供的 Muviz Edge APK 持续修改而来，保留其原始 smali、资源和原生库，以附加 Java 辅助层实现适配。本仓库已经包含此前修改后的完整状态，不需要重新寻找最初 APK 或执行旧目录的补丁脚本。

目标是一个 APK 同时适用于普通手机和横屏车机，提供中文、合理的字体 / 控件大小、随导航栏显隐调整的底部律动，以及可诊断的后台播放恢复。

主要设备场景：Android 11，2560 × 1600，物理 density 160；音乐由车机内安装的音乐 App 播放。150 日志可见 `com.wayfarer.music` 正在播放，其他媒体会话同时存在；不要用导出时单个会话状态推断整段历史。手机兼容场景包含 Android 13 / 小米 10 / HyperOS 1.0.7.0.TJBCNXM。

成功时在首播后约 0.4–1.31 秒观测到有效录音访问从 ignored 变 allowed，importance 仍为 125，随后普通 Visualizer 恢复有效。失败时前台服务 type=130、运行时录音权限已授予，但有效访问仍 ignored。成功与失败中都有初始化 error -3，它是初始化失败记录，不是恢复的必要步骤。心跳约每 30 秒一次，首次非零汇总不等于首帧时间。

启动顺序的共同点是通知监听先在系统运行约 20 秒拉起服务，BOOT_COMPLETED 随后到达；成功既有广播前也有广播后。这排除了“只需固定等待开机完成”的简单判断，不能排除尚未记录的系统资格 / 绑定状态差异。已有增强恢复重复请求的是同一个 AppService，并未完整重建服务；分阶段启动或受控重建仍可作为独立实验，尚无实机结果。

还有这些边界：

- `SERVICE_FOREGROUND` 不等于已取得音频；`CAPTURE_NATIVE_CONFIGURED` 不等于有非零频谱；`RENDER_DRAW` 不等于底边一定在可见区域。
- 进程不运行时无法写日志，不能仅凭没有日志断言系统没有唤醒事件。
- Android 15+ 禁止某些从开机启动的媒体前台服务，当前策略会等待实际界面启动。主要适配 / 实测目标仍为 Android 11 和 13。
- 系统或播放器不向 Visualizer 提供音频时，媒体会话存在也无法生成真实频谱。

## 建议下一步

1. 先按 `docs/BUILD.md` 完成干净编译，确认使用的签名能覆盖已装版本。
2. 在车机覆盖安装 156 后先打开主应用一次，确认只保留 Muviz Edge 主图标、“设置 / 息屏显示”快捷入口消失且应用内设置仍可打开。桌面可能保留旧固定快捷方式，见 `SHORTCUTS153.md`。保持使用情况访问和自动测量开启，继续验证全屏管理工具 / 系统权限页往返及导航栏重新出现时的避让。
3. 问题出现后进入“显示与语言 → 音频与悬浮状态”导出日志。打开界面可能恢复功能，因此应看导出文件里的历史事件，不能只看顶部当前快照。
4. 真正重启或休眠唤醒后，先不进入 Muviz Edge，直接播放并记录延迟。默认保守模式对比进入界面前后的 `CAPTURE_NATIVE_*`、AppOps、`serviceType`、`HEARTBEAT` 的回调年龄、CAPTURE_ACCESS_RESTORED 与 RECOVERY_STATE 的 retryStage。仅在开启增强模式作对照时，再检查 CAPTURE_ACCESS_RECHECK_BEGIN / COMMAND / RESULT、CAPTURE_ACCESS_SCHEDULE 的 fast/slow/exhausted/expired 与 CAPTURE_ACCESS_WAKE 的 accepted/renewed；第 3 次请求后满 60 秒和 180 秒的慢请求属于增强模式，不应期待保守模式出现这些请求。持续拒绝时保留故障历史并按 STARTUP_INVESTIGATION156.md 定位，不以进入界面后的正常快照掩盖之前的失败。
5. 底边异常时同时检查 `NAVIGATION_RELAYOUT`、`NAVIGATION_WINDOW`、`OUTLINE_APPLIED`、`RENDER_DRAW`，先区分系统信号仍旧、没有绘制、窗口裁剪和底边映射错误。日志空洞现在导出为 LOG_GAP；不能把空洞附近缺失的事件当成从未发生。

下一轮保持原逻辑作为对照，先补首帧、权限变化监听和启动阶段诊断，再分别试验启动阶段调整或一次受控服务重建；见 STARTUP_INVESTIGATION156.md。不能把增加请求次数等同于验证了所有启动策略。151–155 原始 smali 和服务注册顺序未变；AOSP 重复前台化存在资格重新评估分支，但第一次自动重试前已经受限，因此不能据此断言回归根因。检查 PROCESS_EXIT_HISTORY 的 PID、reason 与时间，不把旧版本退出记录当成本次崩溃。

## 157 接手重点
