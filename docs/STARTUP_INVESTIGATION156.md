# 156 开机后台采集间歇失败复核

记录日期：2026-10-05。范围：用户提供的 7 份 2026-10-03 / 04 导出日志与当前 156 源码。本轮只修正文档、提出可区分假设的实验，没有修改 APK 行为或发布新包。

## 结论

后台自动采集确实能成功，也确实会持续失败到用户进入 Activity。现有证据支持“首次后台录音访问生效存在条件差异”，不支持“必须有可见 Activity、应用已无优化空间”，也不足以证明某个车机系统服务或某段应用代码就是唯一根因。

录音运行时权限 granted、前台服务 type=130 与 RECORD_AUDIO 的有效 AppOp 是不同观测量。失败时前两者成立，而有效查询仍为 ignored，Visualizer 初始化反复失败。相同 importance=125 只是相同的粗粒度进程重要级，不代表系统内部录音 capability、服务资格、临时豁免或绑定关系完全相同。日志字段名 uidImportance 实际来自 ActivityManager.getMyMemoryState 的进程 importance。

## 样本归并与计时

按 session（含 PID）、系统启动计数去重，不能把不同导出的重叠历史算成新一次启动。小米手机日志单列：它在前台打开应用后测试媒体来源过滤，不能计入车机开机样本。跨开机与同次开机中的进程重启也分别统计。

156 车机可核对到 5 段进入界面前已经采集到非零 FFT 的会话和 2 段失败到进入界面的会话。5 段成功包括 1 次覆盖安装与 4 次真正重启；其中 4 段保守、1 段增强。2 段失败分别处于增强和保守模式。增强失败段开头已被轮转截断，缺少本段 PROCESS_START 和最初播放时间，不能当作完整冷启动实验。缺失的 boot 980–982 不能补算为成功或失败。

这是现有样本分布，不是可靠的设备失败率，更不能由 2/7 推广出“三成开机失败”。

较早的 154 也有覆盖安装 / 真正重启后台成功，以及 boot 973 的失败，成功不是 156 首次出现。155 的 boot 975 / PID 5655 在首次开机后播放约 27.6 秒仍未恢复，进入界面后恢复；同一 boot 的 PID 23576、23727 是随后进程重启，其中 23727 播放约 13 秒后进入界面。不能把 155 压缩成“只有 23727 一次失败”；上述样本也不能证明如果再等更久绝不会恢复。boot 976 / PID 5583 没有观察到播放，不能计作采集失败，更不能据此断言设备绝对没发出任何声音。

## 可以重复核对的规律

1. 五段成功都先处于 effective=1，第一次播放后约 0.4–1.31 秒观测到 effective=0，importance 仍为 125，随后普通采集重建得到 FFT；这些会话进入界面前只记录了一次初始 SERVICE_FOREGROUND，未依赖额外自动前台化成功。
2. 两段失败不是服务完全没启动：服务、通知监听、音频回调与窗口仍在；有效访问停在 1。PID 5469 的 4 次采集修复都失败；PID 5640 可见 attempts=26…31，并有增强请求预算已用尽的历史状态。不能由全局 attempts 反推半小时连续失败，之前可能暂停、成功或缺失日志。
3. 成功不以 BOOT_COMPLETED 已到为必要条件。boot 977 / 979 在广播前恢复，boot 978 在广播后约 46 秒首次播放也恢复；boot 983 在广播后约 7 秒首次播放却未恢复。“统一延迟到开机后某个秒数”尚无稳定阈值证据。
4. 服务通常由 notification_connected 在系统运行约 20 秒时先创建、前台化并注册播放回调，BOOT_COMPLETED 较晚到达。这个顺序在成功和失败中都有，因此是值得做对照的启动阶段，而不是已证明的故障原因。
5. Wayfarer 在成功和失败中都有；154 中酷狗也有成功与失败。最近一次失败首播前的前台是 AVM，成功段首播前可见 HUD，但较早 HUD 场景也失败，不能将 AVM 或某播放器直接判为根因。所有这些车机会话记录的 UID 一致。
6. 已恢复的完整 156 会话中未见有效访问从 0 再退回 1。最近 boot 984 长时间后台仍有新鲜非零 FFT。优先调查首次取得后台资格的阶段，保留已经有效的持续播放恢复机制。

## 现有代码做了什么、还没有试什么

- ServiceRecovery.created 立即 promote；ready 后 PlaybackRecovery 开始工作。当前首次服务来源通常是通知监听。
- ServiceRecovery.boot 调 reconcile。已有服务在保守模式下不再自动请求资格重评估；类型相同也不重复 promote。增强模式按预算重新 startForegroundService，再向同一个 AppService 发送命令并强制前台化。
- 原始 AppService actionType=1 直接返回。增强请求不是完整销毁 / 新建 ServiceRecord 或 AppService 实例。
- actionType=5 更新媒体来源与界面，辅助入口唤醒监控；它不是专门的授权操作。成功与失败都出现这类命令，邻近权限翻转不能证明其因果关系，也不能排除它作为多个系统条件之一参与状态刷新。
- PlaybackRecovery 的普通修复重建 Visualizer；有效访问从 1 变 0 后 accessRevision 会解除旧退避。它解决“资格已经恢复，采集对象仍旧”的问题，不能通过无限重建来授予权限。

Android 11 AOSP ActiveServices.shouldAllowWhileInUsePermissionInFgsLocked 除了可见 Activity，还检查系统调用方、临时允许、相关启动令牌、白名单等条件；OomAdjuster 根据服务的 mAllowWhileInUsePermissionInFgs 和 microphone 类型计算能力。因此 importance=125 与有无后台录音能力不是一一对应。车机 ROM 是否沿用这些条件未知，当前日志也没有记录该内部字段。

参考源码：[ActiveServices.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-11.0.0_r48/services/core/java/com/android/server/am/ActiveServices.java)、[OomAdjuster.java](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-11.0.0_r48/services/core/java/com/android/server/am/OomAdjuster.java)。

## 下一轮有区分力的优化方向（尚未实现）

先增加关键阶段的持久诊断，再做单变量对照，避免同时改变多条恢复链而无法归因。

1. 记录每轮首播、首次 FFT / 非零 FFT、首次窗口实际显示与服务实例代号；在 AppOp 变化监听和启动 / 解锁 / 服务阶段记录权限状态、运行时长、前后台状态、模式、音频会话与回调状态。AppOp 监听需要验证 API 30 支持并保留轮询兜底；不能把它当成授权动作，也不能假定能读到系统内部资格。对使用情况事件同时保留查询时间和事件时间。诊断应标明首帧来自悬浮采集还是 Activity 预览。
2. 保留成功时的普通采集重试。持续播放、从未得到有效采集、已过启动稳定窗口且有效访问持续 ignored 时，才允许实验恢复；最近 FFT、用户主动关闭、屏幕休眠、权限缺失均应阻止干预。
3. 对“通知监听过早建立的服务资格可能被保留”做独立试验：推迟首次采集服务的建立到已解锁且实际播放 / 启动阶段稳定时，或在确认失败后完整重建一次现有采集服务。两者分开测试，不与增大重试次数混为一谈。完整重建需跨实例保留实验预算、清理旧窗口 / 回调、处理晚到命令、确认新实例、限每个真正开机 / 唤醒周期至多一次；必须保留原逻辑作为对照。此方案可能仍被系统拒绝，当前没有实机修复证据。
4. 聚合重复相同的 -3 堆栈，保留首次错误、次数、最近时间和状态变化；为开机摘要单独保留有限空间，总日志仍控制 2 MiB，避免关键开头再次被覆盖。boot 983 / 984 的退出历史返回 0 条，不能凭此证明未被系统终止。

如果上述对照仍不能解释资格差异，需要失败当时的系统错误报告或系统服务诊断，才能看到 ROM 的录音资格判定；单靠应用日志不能识别任意第三方 / 系统服务何时加载完成。通知点击恢复可作为兜底，但不是已经证明唯一可行的方案。
